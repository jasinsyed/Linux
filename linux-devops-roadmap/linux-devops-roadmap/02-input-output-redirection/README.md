## 🎯 Introduction

Input/output redirection is one of the most important concepts in Linux.

Whenever you execute a Linux command, it normally receives input from somewhere and produces output.

For example:

```bash
ls
```

The command displays the directory contents on your terminal.

But imagine you're working as a DevOps engineer on an AWS EC2 production server.

You need to:

- Save application output into a log file.
- Append new logs without deleting old logs.
- Capture errors separately from normal output.
- Suppress unnecessary terminal output.
- Read input directly from a file.
- Generate configuration files automatically.
- Connect multiple commands together to troubleshoot production issues.

This is where **Linux Input/Output Redirection** becomes essential.

Instead of displaying everything on the terminal, you can control where the input and output of commands go.

## 1. Understanding Standard Input, Output, and Error

Before learning redirection commands, you must understand three standard Linux streams.

Linux provides three standard file descriptors for almost every process.

| File Descriptor | Name | Purpose | Default Destination |
|---|---|---|---|
| `0` | stdin | Standard Input | Keyboard / terminal |
| `1` | stdout | Standard Output | Terminal |
| `2` | stderr | Standard Error | Terminal |

### 1. Standard Input (`stdin`)

**Purpose:** Provides input to a command.

For example:

```bash
cat
```

When you execute this command, the terminal waits for you to enter text.

```text
Hello Linux
Learning DevOps
```

Press `Ctrl + D` to indicate the end of input.

The command displays the text you entered.

Here, your keyboard is providing standard input.

### 2. Standard Output (`stdout`)

**Purpose:** Displays the normal output produced by a command.

Example:

```bash
ls
```

Output:

```text
Documents
Downloads
Pictures
Videos
```

This is standard output.

### 3. Standard Error (`stderr`)

**Purpose:** Displays error messages generated by a command.

Example:

```bash
ls /nonexistent_directory
```

Possible output:

```text
ls: cannot access '/nonexistent_directory': No such file or directory
```

This is standard error.

### Real-World Scenario

Imagine you're a DevOps engineer troubleshooting an application on an EC2 server.

You execute:

```bash
ls /var/www/myapp
```

If the directory exists, Linux displays its contents through `stdout`.

If the directory does not exist, Linux displays an error through `stderr`.

**DevOps Insight:** Understanding the difference between `stdout` and `stderr` is essential because production scripts often need to store normal output and errors in separate files.

## 2. `echo` – Display Text

**Purpose:** Displays a line of text or the contents of a variable.

### Syntax

```bash
echo TEXT
```

### Example

```bash
echo "Welcome to Linux"
```

Output:

```text
Welcome to Linux
```

### Display Variables

You can also display the contents of shell variables.

```bash
name="Jasin"

echo "$name"
```

Output:

```text
Jasin
```

### Important Options

| Command | Description |
|---|---|
| `echo "Hello"` | Displays text |
| `echo -n "Hello"` | Does not print the trailing newline |
| `echo -e "Hello\nLinux"` | Interprets supported escape sequences in common shells |

### Understanding `echo -n`

Normally, `echo` prints a newline after the text.

```bash
echo "Hello"
echo "Linux"
```

Output:

```text
Hello
Linux
```

Now use:

```bash
echo -n "Hello"
echo "Linux"
```

Output:

```text
HelloLinux
```

The `-n` option prevents the first command from adding a newline.

### Understanding `echo -e`

The `-e` option enables interpretation of escape sequences in shells that support it.

Example:

```bash
echo -e "Hello\nLinux"
```

Output:

```text
Hello
Linux
```

Common escape sequences:

| Escape Sequence | Meaning |
|---|---|
| `\n` | New line |
| `\t` | Horizontal tab |
| `\b` | Backspace |
| `\\` | Literal backslash |

### Real-World Scenario

Imagine you're creating a basic deployment script.

You want to display deployment progress.

```bash
echo "Starting deployment..."
echo "Installing dependencies..."
echo "Starting application..."
echo "Deployment completed."
```

Output:

```text
Starting deployment...
Installing dependencies...
Starting application...
Deployment completed.
```

This helps developers understand which stage of the deployment is executing.

**DevOps Insight:** `echo` is frequently used in shell scripts for status messages and debugging. For predictable formatting in production scripts, prefer `printf` because `echo -e` behavior can vary between shells.

Example:

```bash
printf "Deployment started\n"
```

## 3. Output Redirection (`>`)

**Purpose:** Redirects the standard output of a command into a file.

Instead of displaying the command output on the terminal, Linux writes it into a file.

### Syntax

```bash
command > filename
```

### Example

```bash
echo "Welcome to DevOps" > output.txt
```

Now inspect the file:

```bash
cat output.txt
```

Output:

```text
Welcome to DevOps
```

The text was written into `output.txt` instead of being displayed directly by the `echo` command.

### Important Concept: Overwriting

The `>` operator overwrites existing file content.

Suppose `output.txt` already contains:

```text
Learning Linux
```

Now execute:

```bash
echo "Learning DevOps" > output.txt
```

Check the file:

```bash
cat output.txt
```

Output:

```text
Learning DevOps
```

The previous content has been replaced.

**Important:** If the file does not exist, Linux creates it. If it already exists, its contents are truncated before the new output is written.

### Real-World Scenario

Imagine you're a DevOps engineer working on an AWS EC2 server.

Your application produces deployment information, and you want to save the latest deployment status.

```bash
echo "Deployment started" > deployment.log
```

Now inspect the file:

```bash
cat deployment.log
```

Output:

```text
Deployment started
```

You have saved the deployment message into a log file.

### Another Production Example

Suppose you want to save the list of running processes.

```bash
ps aux > processes.txt
```

Now inspect the saved information:

```bash
cat processes.txt
```

This allows you to examine the process list later without rerunning the original command.

**DevOps Insight:** Use `>` when you intentionally want to create a fresh output file. Be careful when redirecting to an existing production log or configuration file because its previous contents will be overwritten.

## 4. Append Output (`>>`)

**Purpose:** Appends command output to the end of an existing file without deleting its previous contents.

### Syntax

```bash
command >> filename
```

### Example

First, create a file:

```bash
echo "Application started" > app.log
```

Now append another message:

```bash
echo "Database connected" >> app.log
```

Append one more message:

```bash
echo "Server is running" >> app.log
```

Check the file:

```bash
cat app.log
```

Output:

```text
Application started
Database connected
Server is running
```

### Difference Between `>` and `>>`

| Operator | Behaviour |
|---|---|
| `>` | Overwrites existing content |
| `>>` | Appends content to the end |

### Real-World Scenario

Imagine you're maintaining a production application on an EC2 server.

Every time your deployment script runs, you want to record a new deployment message.

```bash
echo "Deployment started" >> /var/log/deployment.log
echo "Dependencies installed" >> /var/log/deployment.log
echo "Application restarted" >> /var/log/deployment.log
```

Now inspect the log:

```bash
cat /var/log/deployment.log
```

Output:

```text
Deployment started
Dependencies installed
Application restarted
```

The previous deployment messages remain in the file.

### Production Example: Add Timestamps

You can also record timestamps with deployment messages.

```bash
echo "$(date) - Deployment started" >> deployment.log
```

Example output:

```text
Sat Nov 21 10:30:00 UTC 2026 - Deployment started
```

**DevOps Insight:** `>>` is useful for adding application status messages, deployment history, and troubleshooting information to log files. For long-running production applications, use proper log rotation rather than allowing a log file to grow indefinitely.

## 5. Redirect Standard Error (`2>`)

**Purpose:** Redirects error messages generated by a command into a file.

Remember:

- `0` = stdin
- `1` = stdout
- `2` = stderr

The number `2` identifies the standard error stream.

### Syntax

```bash
command 2> error.log
```

### Example

Execute:

```bash
ls /nonexistent_directory 2> error.log
```

Instead of displaying the error on the terminal, Linux saves it into `error.log`.

Now inspect the file:

```bash
cat error.log
```

Possible output:

```text
ls: cannot access '/nonexistent_directory': No such file or directory
```

### Important Concept

The `2>` operator redirects errors only.

It does not redirect normal output.

Example:

```bash
ls /var/www /nonexistent_directory 2> error.log
```

Here:

- The contents of `/var/www` are displayed normally.
- The error from `/nonexistent_directory` is saved in `error.log`.

### Real-World Scenario

Imagine your deployment script executes multiple commands.

Some commands work correctly, but others fail.

You want to capture errors separately so that you can investigate them later.

```bash
mkdir /opt/myapp 2> error.log
```

If the directory creation fails, the error message is saved in `error.log`.

Inspect it:

```bash
cat error.log
```

### Production Troubleshooting Example

Suppose a backup operation fails because the source directory does not exist.

```bash
tar -czf backup.tar.gz /var/www/missing 2> backup_error.log
```

Now inspect:

```bash
cat backup_error.log
```

You can investigate the error without mixing it with normal command output.

**DevOps Insight:** Separating errors from normal output makes production troubleshooting easier. You can collect failures independently and send them to monitoring or alerting systems.

## 6. Append Standard Error (`2>>`)

**Purpose:** Appends error messages to an existing error log instead of overwriting it.

### Syntax

```bash
command 2>> error.log
```

### Example

Execute:

```bash
ls /missing_directory 2>> error.log
```

Now execute another command that generates an error:

```bash
cat /missing_file 2>> error.log
```

Inspect the file:

```bash
cat error.log
```

Both errors are stored in the same file.

### Difference Between `2>` and `2>>`

| Operator | Behaviour |
|---|---|
| `2>` | Overwrites the existing error log |
| `2>>` | Appends errors to the existing error log |

### Real-World Scenario

Imagine your production server runs a backup script every night.

You want to preserve every backup failure for future investigation.

```bash
tar -czf backup.tar.gz /var/www/myapp 2>> backup_errors.log
```

If the backup command fails, the error is appended to the existing file.

When the next backup runs, its errors can also be added without deleting previous ones.

**DevOps Insight:** Persistent error logs are valuable when investigating recurring deployment failures, backup failures, and scheduled job issues.

## 7. Redirect Standard Output and Error

**Purpose:** Redirects both normal output and error messages into the same file.

In production environments, you often need to capture everything produced by a command.

There are multiple ways to do this.

### Method 1: Using `&>`

### Syntax

```bash
command &> output.log
```

### Example

```bash
ls /var/www /missing_directory &> output.log
```

Inspect the file:

```bash
cat output.log
```

The file can contain both:

- Normal directory listing output.
- Error messages.

**Note:** `&>` is a Bash feature.

### Method 2: Using `> file 2>&1`

This is a widely used form in shell scripts.

```bash
command > output.log 2>&1
```

Let's understand it.

```bash
ls /var/www /missing_directory > output.log 2>&1
```

Step by step:

1. `> output.log` redirects standard output (`stdout`) into the file.
2. `2>&1` redirects standard error (`stderr`) to wherever standard output is currently going.
3. Both streams end up in `output.log`.

### Method 3: Append Both Output and Errors

In Bash:

```bash
command &>> output.log
```

This appends both normal output and errors.

Another form:

```bash
command >> output.log 2>&1
```

This also appends both streams.

### Important Concept: Redirection Order Matters

Compare these two commands.

**Command A:**

```bash
command > output.log 2>&1
```

Both standard output and standard error go into `output.log`.

**Command B:**

```bash
command 2>&1 > output.log
```

This behaves differently.

1. `2>&1` first sends standard error to the current standard output, usually the terminal.
2. `> output.log` then redirects standard output into the file.
3. Standard error remains connected to the terminal.

Therefore, errors are not redirected into the file in the second command.

### Real-World Scenario

Imagine you're deploying a Java Spring Boot application on an AWS EC2 instance.

Your deployment command is:

```bash
java -jar app.jar
```

The application may produce:

- Application startup messages.
- Database connection information.
- Configuration errors.
- Runtime exceptions.

You want to capture both normal output and errors.

Execute:

```bash
java -jar app.jar > application.log 2>&1
```

Now inspect:

```bash
cat application.log
```

You can investigate the application's startup and runtime output from one file.

**DevOps Insight:** Capturing both streams is useful when debugging application deployments and scheduled jobs. In production, consider a process manager such as systemd and a centralized logging system instead of relying only on manually redirected files.

## 8. `/dev/null` – Discard Output

**Purpose:** Discards output instead of displaying it or saving it into a regular file.

Linux provides a special device called `/dev/null`.

Anything written to `/dev/null` is discarded.

Think of it as a black hole for command output.

### Syntax

```bash
command > /dev/null
```

### Example

```bash
echo "Hello Linux" > /dev/null
```

Nothing appears on the terminal.

The output is discarded.

### Suppress Normal Output and Errors

```bash
command > /dev/null 2>&1
```

This suppresses both standard output and standard error.

### Real-World Scenario

Imagine you're writing a deployment script.

You want to check whether Docker is installed on your production server.

Execute:

```bash
command -v docker > /dev/null 2>&1
```

This checks whether the shell can locate the Docker command.

You can then inspect the exit status:

```bash
echo $?
```

Output:

```text
0
```

An exit status of `0` indicates success. A non-zero status indicates that the command was not found or another failure occurred.

### Another Example: Quiet Health Check

```bash
curl -fsS http://localhost:8080/health > /dev/null 2>&1
```

This suppresses the response body and error messages.

You can check whether the request succeeded:

```bash
echo $?
```

**DevOps Insight:** `/dev/null` is commonly used in scripts when you need to suppress unnecessary output while still checking command success through its exit status.

Do not discard errors when you need them for production troubleshooting.

## 9. Input Redirection (`<`)

**Purpose:** Takes input from a file instead of reading it from the keyboard.

Normally, a command may receive input from the terminal.

With `<`, you can provide input directly from a file.

### Syntax

```bash
command < filename
```

### Example

First, create a file:

```bash
echo "Linux DevOps Learning" > input.txt
```

Now execute:

```bash
cat < input.txt
```

Output:

```text
Linux DevOps Learning
```

The command receives its input from `input.txt`.

### Another Example

Suppose you have a file containing multiple lines:

```bash
cat > names.txt
```

Enter:

```text
Jasin
Alex
David
```

Press `Ctrl + D` to finish.

Now count the number of lines:

```bash
wc -l < names.txt
```

Output:

```text
3
```

The `<` operator provides the file contents as standard input to `wc`.

### Real-World Scenario

Imagine you're a DevOps engineer working with a production server.

You receive a file containing a list of usernames that need to be processed.

Instead of manually entering each username, you can provide the file as input.

```bash
while read -r username
do
    echo "Processing user: $username"
done < users.txt
```

If `users.txt` contains:

```text
admin
developer
tester
```

Output:

```text
Processing user: admin
Processing user: developer
Processing user: tester
```

### Why Is This Useful?

- Processing multiple records from a file.
- Automating repetitive tasks.
- Reading configuration information.
- Processing lists of users or servers.
- Running batch operations.

**DevOps Insight:** Input redirection is especially useful in shell scripting when processing files automatically without requiring manual keyboard input.

## 10. Here Documents (`<<`)

**Purpose:** Provides multiple lines of input directly to a command without creating a separate input file.

A here document is commonly called a heredoc.

### Syntax

```bash
command << delimiter
line 1
line 2
line 3
delimiter
```

The delimiter marks the end of the input.

### Example

```bash
cat << EOF
Welcome to Linux
Learning DevOps
Understanding Redirection
EOF
```

Output:

```text
Welcome to Linux
Learning DevOps
Understanding Redirection
```

The text between the two `EOF` markers is passed to the command as standard input.

### Real-World Scenario

Imagine you're a DevOps engineer deploying an application.

Your application requires a configuration file.

Instead of manually opening an editor and writing the configuration, you can generate it using a heredoc.

```bash
cat << EOF > application.conf
APP_NAME=MyApplication
APP_ENV=production
APP_PORT=8080
EOF
```

Now inspect the generated file:

```bash
cat application.conf
```

Output:

```text
APP_NAME=MyApplication
APP_ENV=production
APP_PORT=8080
```

You have created the configuration file automatically.

### Important Concept: Variable Expansion

When you use an unquoted delimiter, shell variables are expanded.

Example:

```bash
APP_NAME="MyApplication"

cat << EOF
Application: $APP_NAME
Environment: production
EOF
```

Output:

```text
Application: MyApplication
Environment: production
```

### Prevent Variable Expansion

If you quote the delimiter:

```bash
APP_NAME="MyApplication"

cat << 'EOF'
Application: $APP_NAME
Environment: production
EOF
```

Output:

```text
Application: $APP_NAME
Environment: production
```

The variable is printed literally.

### Why Is This Important?

Sometimes configuration files contain `$` characters that must remain unchanged.

Quoting the delimiter prevents shell parameter and command expansion inside the heredoc.

**DevOps Insight:** Heredocs are useful for generating configuration files, creating deployment scripts, and providing multiline input to commands. Be careful not to expose passwords, API keys, or other secrets in shell history or logs.

## 11. Here Strings (`<<<`)

**Purpose:** Passes a single string directly as standard input to a command.

A here string is similar to a here document, but it is intended for a single string.

### Syntax

```bash
command <<< "string"
```

### Example

```bash
cat <<< "Welcome to Linux"
```

Output:

```text
Welcome to Linux
```

The string is passed to `cat` as standard input, with a newline added.

### Another Example

```bash
wc -w <<< "Learning Linux and DevOps"
```

Output:

```text
4
```

The command counts the words in the supplied string.

### Real-World Scenario

Imagine you're writing a shell script that needs to process a small piece of text.

Instead of creating a temporary file, you can pass the text directly to a command.

For example:

```bash
grep "ERROR" <<< "INFO Application started"
```

There is no matching output because the input does not contain `ERROR`.

Now:

```bash
grep "ERROR" <<< "ERROR Database connection failed"
```

Output:

```text
ERROR Database connection failed
```

### Difference Between Here Document and Here String

| Operator | Purpose |
|---|---|
| `<<` | Provides multiple lines of input |
| `<<<` | Provides a single string as input |

**DevOps Insight:** Here strings are useful for small text-processing operations in Bash scripts. They are not POSIX `sh` syntax, so check which shell your script uses.

## 12. Pipes (`|`)

**Purpose:** Sends the standard output of one command directly as the standard input of another command.

Pipes allow you to combine multiple commands without creating temporary files.

### Syntax

```bash
command1 | command2
```

The output from `command1` becomes the input for `command2`.

### Example

```bash
ls | grep ".log"
```

Explanation:

1. `ls` lists the files in the current directory.
2. The pipe sends the output to `grep`.
3. `grep` filters lines containing `.log`.

Possible output:

```text
app.log
error.log
deployment.log
```

### Another Example

Count the number of files:

```bash
ls | wc -l
```

The output from `ls` is passed to `wc -l`, which counts the lines it receives.

### Real-World Scenario

Imagine you're a DevOps engineer troubleshooting a production application.

Your application generates a large log file containing thousands of entries.

You want to identify errors.

Execute:

```bash
cat application.log | grep "ERROR"
```

This displays matching error lines.

A more efficient approach is:

```bash
grep "ERROR" application.log
```

You can also count matching error lines:

```bash
grep -c "ERROR" application.log
```

Example output:

```text
25
```

This means 25 lines matched the pattern.

### Multiple Commands Using Pipes

You can combine multiple commands.

```bash
cat application.log | grep "ERROR" | wc -l
```

This:

1. Reads the log file.
2. Filters lines containing `ERROR`.
3. Counts the matching lines.

A more efficient version is:

```bash
grep "ERROR" application.log | wc -l
```

### Important Concept: Pipe and Error Output

By default, a normal pipe (`|`) passes standard output, not standard error.

In Bash, you can use:

```bash
command1 |& command2
```

This sends both standard output and standard error into the pipe.

**DevOps Insight:** Pipes are fundamental to Linux troubleshooting. DevOps engineers frequently combine commands such as `grep`, `sort`, `uniq`, `wc`, and `awk` to analyze logs and system information.

# 🚀 Real-World Production Scenario

## Situation: Troubleshooting a Failed Application Deployment on an AWS EC2 Server

Imagine you're a DevOps engineer responsible for deploying a Spring Boot application on an AWS EC2 Ubuntu instance.

Your application deployment is failing.

Your manager asks you to:

1. Execute the deployment command.
2. Save normal output and errors.
3. Preserve previous deployment logs.
4. Investigate failed commands.
5. Generate a configuration file.
6. Check whether the application is healthy.

Let's perform this workflow step by step.

### Step 1: Create a Deployment Log Directory

```bash
mkdir -p /opt/company/backend/logs
```

This creates the required directory structure.

### Step 2: Execute the Deployment Command and Save Its Output

For demonstration, use:

```bash
echo "Starting application deployment..." > /opt/company/backend/logs/deployment.log
```

The `>` operator creates the log file or overwrites its existing content.

### Step 3: Append Additional Deployment Messages

```bash
echo "Installing dependencies..." >> /opt/company/backend/logs/deployment.log

echo "Building application..." >> /opt/company/backend/logs/deployment.log

echo "Starting application..." >> /opt/company/backend/logs/deployment.log
```

The `>>` operator preserves previous messages and adds new ones.

### Step 4: Capture Application Errors Separately

Suppose a deployment command fails because a required directory does not exist.

```bash
ls /opt/company/missing_directory 2> /opt/company/backend/logs/error.log
```

The error is stored separately.

Inspect it:

```bash
cat /opt/company/backend/logs/error.log
```

### Step 5: Capture Both Normal Output and Errors

Now execute a command that produces both normal output and an error:

```bash
ls /opt/company /missing_directory > /opt/company/backend/logs/full.log 2>&1
```

Both streams are saved in `full.log`.

### Step 6: Generate an Application Configuration File

```bash
cat << EOF > /opt/company/backend/application.conf
APP_NAME=SpringBootApplication
APP_ENV=production
APP_PORT=8080
EOF
```

This creates a configuration file automatically.

### Step 7: Verify the Configuration

```bash
cat /opt/company/backend/application.conf
```

### Step 8: Search for Deployment Errors

```bash
grep "ERROR" /opt/company/backend/logs/deployment.log
```

This searches for lines containing `ERROR`.

### Step 9: Count the Number of Errors

```bash
grep -c "ERROR" /opt/company/backend/logs/deployment.log
```

This counts matching lines.

### Step 10: Check Application Health Without Displaying the Response

```bash
curl -fsS http://localhost:8080/health > /dev/null 2>&1
```

Now check the exit status:

```bash
echo $?
```

- `0` means the health-check request succeeded.
- A non-zero value indicates failure.

This example assumes the application exposes a health endpoint at that URL.

### Final Directory Structure

```text
/opt/company/backend/
│
├── application.conf
│
└── logs/
    ├── deployment.log
    ├── error.log
    └── full.log
```

### What Did You Learn From This Scenario?

You used:

- `echo` to display deployment messages.
- `>` to create or overwrite log files.
- `>>` to append deployment information.
- `2>` to capture errors.
- `2>&1` to capture both output streams.
- `/dev/null` to suppress unnecessary output.
- `<<` to generate configuration files.
- `<` and `<<<` to provide command input.
- `|` to connect commands and analyze logs.

**DevOps Insight:** Input/output redirection is not just a Linux command-line feature. It is a fundamental part of deployment automation, application troubleshooting, shell scripting, and production log management.

| `2>` | Redirects stderr and overwrites a file |
| `2>>` | Redirects stderr and appends to a file |
| `&> file` | Redirects stdout and stderr in Bash |
| `> file 2>&1` | Redirects stdout and stderr |
| `> /dev/null` | Discards stdout |
| `> /dev/null 2>&1` | Discards stdout and stderr |
| `< file` | Reads standard input from a file |
| `<< EOF` | Provides multiline input |
| `<<< "text"` | Provides a string as input in Bash |
| `\|` | Sends stdout to another command |
| `\|&` | Sends stdout and stderr to another command in Bash |
